# 数据备份与恢复

> 一句话：**每天自动导一份 JSON 快照存到本地/网盘，出事时一条命令恢复。**
> 备份脚本已验证过完整的「导出 → 清空 → 回灌 → 再导出」往返，数据逐字段一致。

---

## 一、为什么不能只依赖 Supabase 自带的备份

Supabase 的**时间点恢复（PITR）是付费功能**，免费项目拿不到自助恢复能力。
也就是说，在当前的免费套餐下，「靠平台备份」约等于**没有备份**。
本项目自带的这套脚本不依赖套餐等级，导出物是普通 JSON，本地存一份就有一份。

### 两套备份各自的定位

| | 平台侧（Supabase） | 本项目脚本 |
|---|---|---|
| 覆盖范围 | 全库物理备份 | 17 张业务表 |
| 能否自助恢复 | 免费版**不能** | 能，一条命令 |
| 出事时能否先看内容 | 不能（要整库恢复才知道） | 能，文本编辑器直接打开 |
| 离线留存 | 不能 | 能，拷到网盘即可 |
| `auth.users`（登录账号） | **包含** | **不包含** |
| 保留粒度 | 平台策略 | 你自己定 |

**关键差异**：脚本**不导出 `auth.users`**（Supabase 托管系统表，无法通过
REST API 读取）。所以脚本备份恢复后，会员档案、余额、预约、流水都会回来，
但**登录账号需要另行处理**（见第五节）。

## 二、日常备份

```bash
npm run backup
```

产物落在 `backups/linzi-care_<时间戳>/`，每张表一个 JSON 文件，外加
`_manifest.json`（记录行数、列名、恢复顺序）。

`backups/` 已在 `.gitignore` 中排除 —— **快照里有会员手机号，绝不能提交**。

### 只保留最近 N 份

```bash
npx tsx scripts/db-backup.mts --keep 30
```

### 存到别处（推荐指向网盘同步目录）

```bash
npx tsx scripts/db-backup.mts --out "D:\OneDrive\linzi-backup" --keep 30
```

### 校验快照完整性

```bash
npm run backup:verify -- backups/linzi-care_2026-10-15_04-18-35
```

检查文件是否齐全、行数是否与清单一致（能发现拷贝中断导致的半截文件）。

### 建议的自动化

Windows 计划任务每天凌晨跑一次即可：

```bat
cd /d E:\code\linzi-care
npx tsx scripts/db-backup.mts --out "D:\OneDrive\linzi-backup" --keep 30 >> backup.log 2>&1
```

## 三、故障恢复

### 第一步：先预演，别急着写库

```bash
npm run restore -- backups/linzi-care_2026-10-15_04-18-35
```

**默认不写库**，只列出将要执行的 `DELETE` / `INSERT` 清单。
恢复往往发生在最慌的时刻，所以这一步是强制的：确认清单没问题再往下走。

### 第二步：真正恢复

```bash
npx tsx scripts/db-restore.mts backups/linzi-care_2026-10-15_04-18-35 --apply
```

脚本会重建全部 17 张表的数据。

**跨项目恢复会被拒绝**：若快照来源与当前 `SUPABASE_URL` 不一致，
脚本会中止并提示 —— 这是为了防止「想恢复到测试库结果写进了生产库」。
确实需要跨库时加 `--force`。

### 第三步：恢复后核对

```bash
# 行数应与快照清单一致
npm run backup -- --out .check

# 然后人工确认这两项
#   - 会员余额是否对得上
#   - 预约数量是否符合预期
```

## 四、验证备份真的能用

**未经恢复验证的备份不算备份。** 出事时才发现恢复不了，是最糟的情况。

```bash
npm run verify:backup
```

它会真的走完「导出 → 清空 → 回灌 → 再导出 → 逐字段比对」全流程。
耗时约 1 分钟（当前数据量 585 行）。

⚠️ 这个测试**会清空并重写业务表**，脚本默认拒绝在生产库上运行。
在本地或分支库上跑。

建议在**每次改完数据库结构（新增迁移）之后**跑一次 —— schema 变了，
备份脚本的假设可能就不成立了（本项目就踩过：`staff_services` 是复合主键、
`balance_logs.delta` 是生成列，都会让恢复失败，现已分别处理）。

## 五、`auth.users` 怎么办

脚本不导出登录账号，所以有两件事要单独准备：

1. **账号清单**：哪些邮箱能登录、分别是什么角色。
   建议定期从后台「员工管理 / 会员管理」页导出一次，或直接记在密码管理器里。

2. **恢复办法**（二选一）：
   - **推荐**：恢复到新库后，老板登录后台用「录入新会员 / 录入新员工工号」
     重新建号，系统会重新生成 `auth.users` 记录。
     `profiles` / `user_roles` 已由快照恢复，重建后只需重新关联。
   - 若原库仍可访问：在 Supabase 控制台 Authentication → Users 页面
     手动重新创建，或联系 Supabase 支持导出用户列表。

> 这也说明：**不要把唯一的账号凭证只存一份**。老板自己的登录口令请记在
> 密码管理器里 —— 库没了还能重建，口令忘了就进不去后台了。

## 六、相关文件

| 文件 | 作用 |
|---|---|
| `scripts/db-backup.mts` | 导出快照，支持 `--out` / `--keep` / `--verify` |
| `scripts/db-restore.mts` | 恢复快照，默认预演，`--apply` 才写库 |
| `scripts/verify-backup-roundtrip.mts` | 往返测试，证明备份可恢复 |
| `supabase/migrations/` | 表结构定义（恢复前应确保已应用全部迁移） |

> ⚠️ 恢复的前提是**库的 schema 与快照一致**。若快照来自旧版本、之后又加了
> 新迁移，请先把迁移推完再恢复，否则可能出现列不匹配。
