# GUI Acceptance Audit — 2026-10-13

Full-surface audit of the member, staff, and owner consoles, driven through a real
browser against a production build backed by the live Supabase project. Every flow
was performed as a real user (real clicks and typing); no mocks, no injected state.

Method: black-box GUI testing. Source was not modified during the audit — issues
were recorded, then fixed afterwards in separate commits.

Viewports: 1440×900 desktop and 390×844 mobile.

## Bugs

### BUG-001 — Store address contains corrupted characters

The shared `SiteFooter` (member, staff, and admin) rendered the store address as
`广州市增城区新塘镇国贸汇妖腰* 林梓·头疗美容养生`. `妖腰` is meaningless text and
`*` was an unfilled shop-unit placeholder.

**Root cause:** `0004_seed.sql` documents that `*` marks a unit number still to be
filled in, but the comment text was written into the address value itself.

**Fix:** migration `0019_fix_store_address.sql` corrects the live row and `0004` is
amended so a fresh environment does not reproduce it. The update is conditional
(`where address like '%妖腰%'`) so a real unit number entered later is never
overwritten.

### BUG-002 — Appointment dialog shows list price, not the charged member price

The owner's "handle this booking" dialog displayed `45分钟 · ¥68` while the booking
actually charged ¥38 (member price); `balance_logs` recorded
`预约扣费 · 姜汤头疗 ¥-38, 结余 ¥92→¥54`.

**Root cause:** `appointment-dialog.tsx` read `services.price`. The same rule was
independently reimplemented in the dashboard and reports pages. Migration `0014`
already established the correct precedent — snapshot first, member price before
list price — precisely because reading `services.price` "gets the money wrong in
both directions".

**Fix:** a single canonical `bookedPrice()` in `lib/format.ts`
(`member_price_snapshot ?? price_snapshot ?? member_price ?? price`). All three call
sites now use it instead of local copies.

Verified against real data: the row carries `price_snapshot = 68` **and**
`member_price_snapshot = 38`; the new logic returns 38, matching the ledger.

### BUG-006 — Member-creation dialog overlaps the credentials dialog

After creating a member, the one-time credentials dialog appeared while the
creation form stayed mounted. Both portals used `z-index: 50`, so the form's text
bled through the credentials panel's lower edge.

**Fix:** unmount the creation dialog, then mount the credentials dialog on the next
animation frame. Measured across the submit transition: the dialog count is now a
constant 1, where it previously reached 2.

### BUG-008 — Admin tables overflow horizontally on mobile

At 390px the members table's entire action column (balance / ledger / passes /
edit / reset password / suspend / delete) sat off-screen behind a horizontal
scroll. Measured: a 356px container holding 545px of content, with the first
action button at x=476.

**Fix:** `DataTable` gains an optional `renderMobileCard`. Below `md` it renders
one card per row; at `md` and above the full table is unchanged. Wired into the
members, staff, services, and products tables. Vertical card stacking was chosen
over horizontal scrolling because a scroll container hides actions behind a
gesture no one discovers.

## Polish items

**UX-003** — Landing on `/book?service=<id>` did preselect the service, but the
page stayed at the top with the selected card below the fold, so users assumed the
click had failed. Now the card scrolls into view and pulses once. Only triggers on
an explicit `?service=`; draft restore stays quiet.

**UX-004** — Home said "三步完成预约" while `/book` said "四步". Unified to four.

**UI-007** — Long names (e.g. `姜汤头疗+头皮排污`) pushed the category badge to a
second line at the card's left edge and squeezed the price column. Name and badge
now occupy separate lines, and the price column is `shrink-0 whitespace-nowrap`.

## Negative finding (not a product defect)

**Booking submission appeared to hang in the audit browser.** The first booking
submitted normally; the second did not respond to clicks, with the button's rect
at `top: 938` against a 900px logical viewport and `elementFromPoint` returning
null. Confirmed via `/my` that no second booking was created and the balance was
unchanged — so this was not a silent success, and it did not reproduce outside
this browser session. The cancel path is covered by the E2E suite
(`GIVEN 挂起单 WHEN 顾客自取消 THEN 状态变为 cancelled`), which passes.

## Verified working (no issues found)

- **Cross-console data flow**, tracked end to end on booking `LZ-3F06B978`:
  member books → owner sees it in the pending queue (sidebar badge `1`) → owner
  confirms (badge drops to 0 in the same tick, bell dot clears) → staff sees it as
  confirmed with only the three permitted actions → staff advances
  `confirmed → arrived → done` → member sees it move to history as 已完成.
- **Booking state machine**: terminal states correctly remove every action; staff
  never sees confirm or cancel, matching the documented permissions.
- **Slot conflict engine**: on 10/15 for 林小梓 the existing 15:30–16:15 booking
  excluded exactly 15:00, 15:30, and 16:00 while leaving all other slots open.
- **Balance audit**: a +¥50 adjustment wrote `充值入账 +¥50, 结余 ¥54→¥104` and
  stayed consistent across owner, member, and report views.
- **Role isolation**: member → `/admin` lands on `/my`; staff → `/admin` and `/my`
  land on `/staff`; unauthenticated → `/login?next=…`.
- **Login errors** name no account existence ("邮箱或密码不正确").
- **Credentials dialog**: 16-character password shown once, with copy and
  acknowledge actions.
- **Mobile**: home, services, shop, booking, `/my`, staff console, admin dashboard,
  login, and the drawer menu were all clean at 390px.

## Environment note

The E2E suite runs against the same live database real users are transacting on.
During the audit the test member's balance drifted to ¥28 — below the ¥38 needed
for a booking — which failed `create_appointment` and cascaded into 14 reported
failures. PostgREST dressed this up as
`Could not find the function public.update_appointment_status(p_status) in the
schema cache`, which is a misleading symptom rather than the cause. Restoring the
balance returned the suite to 37/37.

`scripts/reset-e2e-baseline.ts` restores that baseline through the normal owner
RPC. Longer term this suite should run against a dedicated Supabase branch, since
any concurrent human activity can drift it.
